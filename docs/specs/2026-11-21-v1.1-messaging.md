# Soma Relay v1.1: complete messaging

Date: 2026-11-21. Extends [2026-11-21-soma-relay-design.md](2026-11-21-soma-relay-design.md). The owner asked for a complete messenger: notifications, location sharing, polls, link previews, document viewing (PDF, PowerPoint, Word and more), and a polished UI with good animations.

The core is schema-agnostic (an `AppMessage` is any JSON object), so everything here lives in the clients and the node. Every client must ignore kinds and fields it does not know, and must never show "unreadable" for an unknown kind.

## 1. New message kinds and fields

All fields are snake_case JSON. `id` is a uuid v7, `ts` is ms since epoch, as before.

### Reactions (format already used by the web client)

```
{ kind: "reaction", text: "👍", reply_to: "<target id>" }     // text "" removes mine
```
One reaction per person per message: a new one replaces the old one.

### Edit and delete for everyone

```
{ kind: "edit",   reply_to: "<target id>", text: "new text" }
{ kind: "delete", reply_to: "<target id>" }
```
Only accepted from the original sender (check the sender fingerprint, and in groups the group sender). Edit: within 24 h of the original, text messages only; the bubble shows "modifié". Delete: the bubble becomes "Message supprimé" and its media is removed from disk.

### Forward

Any message can be re-sent to another conversation with `forwarded: true`. Media is re-sent with the same attachment key and blob URL (no re-upload).

### Polls

```
{ kind: "poll", poll: { question: "Resto ce soir ?", options: [{ id: "a", text: "Thaï" }, ...],
                        multi: false, closes_at?: ms } }
{ kind: "poll-vote", reply_to: "<poll id>", vote: ["a"] }        // [] retracts
```
2 to 12 options, option ids are short strings unique in the poll. Latest vote (by `ts`) per voter wins. Results are counted locally from the votes received; every member sees the same counts once the votes arrive. The creator may close the poll with `{ kind: "poll-vote", reply_to, vote: [], close: true }`; votes after `closes_at` or a close are ignored.

### Location

```
{ kind: "location", location: { lat, lon, accuracy_m?, name?, address?, live_until?: ms } }
{ kind: "location-update", reply_to: "<location message id>",
  location: { lat, lon, accuracy_m?, heading?, stop?: true } }
```
Static pin: `live_until` absent. Live sharing: 15 min, 1 h or 8 h; the sender emits an update at most every 10 s while moving more than 10 m, and a final `stop: true`. Updates are not stored as bubbles: they move the pin of the original message. Updates after `live_until` are ignored.

### Link previews

A text message may carry a preview generated by the sender (the receiver never fetches anything):

```
{ kind: "text", text: "regarde https://…", link: { url, title?, description?, site?,
  image?: "<base64 JPEG, longest side 600 px, <= 40 KiB>" } }
```
iOS builds it with `LPMetadataProvider`. The web client asks its node: `GET /v1/preview?url=` (see section 3). Previews are on by default and can be turned off in Settings. Only `http(s)` URLs, first URL in the text.

### Documents

Documents stay `kind: "file"` with the usual attachment. New optional attachment fields: `pages?: int` and a `thumb` made by the sender (first page of a PDF, QuickLook thumbnail on iOS, pdf.js first page on web). Viewers:
- iOS: QuickLook (`QLPreviewController`) for PDF, Word, PowerPoint, Excel, Keynote, Pages, Numbers, RTF, text, images, USDZ. Share sheet and "save to Files".
- Web: PDF with pdf.js (pages, zoom), Word (`.docx`) with docx-preview, Excel (`.xlsx`, `.csv`) with SheetJS as a table, PowerPoint (`.pptx`) with a slide renderer if one works offline in the browser, else the thumbnail plus download. Text and code files shown as text. Everything else: download.

### Disappearing messages

```
{ kind: "settings", settings: { expire_s: 0 | 300 | 3600 | 86400 | 604800 } }
```
Sent in a conversation, it sets the timer for both sides (a system line says who changed it). Each later message carries `expire_s`. A message is deleted `expire_s` after it was first seen by its reader (sender: after it was sent). Media goes with it.

### Mentions (groups)

`mentions: ["<fingerprint>", ...]` on a text message; the text contains `@Name`. A mention bypasses a muted group's notification.

## 2. Notifications

### On device

- iOS: a notification for every incoming message when the app is not showing that conversation (sender name and text, or "Photo", "Sondage : …" and so on), grouped per conversation (`threadIdentifier`), with Reply and Mark as read actions. Settings: show previews (on, off: "Nouveau message"), per-conversation mute (1 h, 8 h, 1 week, always). Badge = unread count.
- Web: Notification API when the tab is hidden, same text rules.

### Push through the node

When the app is closed, the node wakes it. The push never carries content or sender:

- Client -> node, after `ready`:
  `{"t":"push","kind":"apns","token":"<hex device token>","env":"prod"|"sandbox"}` or
  `{"t":"push","kind":"webpush","sub":{"endpoint":"…","keys":{"p256dh":"…","auth":"…"}}}` or
  `{"t":"push","kind":"none"}` to unregister. Node answers `{"t":"push","ok":true}`.
- The node sends a push when it stores an envelope for a mailbox that has no live connection, at most one per mailbox every 30 s.
- APNs: HTTP/2 to `api.push.apple.com` (or sandbox), token auth (ES256 JWT from a `.p8` key), payload `{"aps":{"alert":{"title":"Soma Relay","body":"Nouveau message"},"sound":"default","mutable-content":1}}`, topic = bundle id, priority 10, `apns-push-type: alert`, collapse id `relay`. A 410 or `BadDeviceToken` removes the token. Config: `RELAY_APNS_KEY_P8` (PEM text or path), `RELAY_APNS_KEY_ID`, `RELAY_APNS_TEAM_ID`, `RELAY_APNS_TOPIC`. Without them, APNs is off and `push` with kind apns answers `{"t":"push","ok":false,"reason":"apns_off"}`.
- Web Push: VAPID keys generated by the node on first start and kept in the data dir, public key at `GET /v1/push/vapid` (`{"key":"<b64url>"}`). Payload encrypted per RFC 8291 (aes128gcm), content `{"t":"wake"}`, TTL 1 day, urgency high. 404/410 removes the subscription.
- iOS: no Notification Service Extension in v1.1, because an extension cannot advance the ratchet safely while the app may run too. The push shows "Nouveau message". The app fetches and decrypts on open, on a silent wake, or in a `BGAppRefreshTask`. Notifications with sender and text come from local notifications posted by the app.

## 3. Node additions

- `push` frame and senders above, tokens in SQLite (`push(mailbox PK, kind, token, env, sub_json, updated_at)`).
- `GET /v1/push/vapid`.
- `GET /v1/preview?url=<http(s) url>`: fetches the page (8 s timeout, 2 MiB max, 5 redirects max, only http/https, refuses private, loopback, link-local and metadata IPs after DNS resolution and on every redirect), parses Open Graph, Twitter card and `<title>`/`<meta name=description>`, fetches `og:image` with the same rules and returns it as a JPEG data URL shrunk to <= 600 px (or the original if it is already a small JPEG/PNG/WebP under 40 KiB). Response `{url, title, description, site, image}`. Rate limited per IP. Never logs URLs.

## 4. UI and motion quality bar

The goal is a chat that feels as good as iMessage and Telegram. Both clients:

- Bubbles: grouped runs (tail only on the last bubble of a run, tighter spacing inside a run), date separators ("Aujourd'hui", "Hier", weekday, date), unread separator, sender names in groups with a stable color per person.
- Sending: the new bubble springs up from the composer (iOS `.spring(duration: 0.35, bounce: 0.2)`, web equivalent with CSS/WAAPI), the status line fades from "EN ROUTE" to "REÇU" to "LU".
- Long press (iOS `.contextMenu` with a preview, web right click / long press): a reaction strip (👍 ❤️ 😂 😮 😢 🙏 and "+" for any emoji), then Reply, Copy, Forward, Edit (mine, text, 24 h), Delete for me, Delete for everyone (mine), Info (path, times).
- Swipe right on a bubble to reply, with a haptic tick at the threshold (iOS), and a quoted reply in the composer.
- Reactions shown as a small pill under the bubble with a pop animation.
- Typing indicator: three dots that bob, in a bubble.
- Scroll-to-bottom button with an unread count when the user has scrolled up; tapping a reply quote scrolls to and flashes the original.
- Composer: grows to 6 lines, send button morphs from mic to arrow, attachment menu with Photo, Camera, Document, Location, Poll, and a hold-to-record voice note with slide to cancel.
- Search: in the conversation list (names and message text, local only) and inside a conversation (jump between hits).
- Empty, loading and error states for every screen; no layout jumps when images load (reserve the aspect ratio from the thumbnail).
- Accessibility: Dynamic Type, VoiceOver labels on every bubble and control, Reduce Motion replaces springs with fades, contrast checked in light and dark.
- Haptics (iOS): send, reaction, swipe-to-reply threshold, poll vote, errors.

## 5. Out of scope for v1.1

Payments, stickers and GIF search, stories, multi-device, message content in push payloads, Android.

## 6. Profile (v1.2)

Added 2026-11-21. A person can set a photo, and a group admin can set a group photo. Like every kind above, these live only in the clients: the core and the node see sealed envelopes.

### Profile

```
{ kind: "profile", profile: { name?: string, avatar?: "<base64 JPEG>" | null, avatar_hash?: "<hex sha256>" } }
```

- The photo is cropped square by the sender, resized to 256 x 256 px and encoded as a JPEG of at most 24 KiB (lower the quality until it fits). `avatar_hash` is the lowercase hex SHA-256 of the JPEG bytes (not of the base64 text).
- `avatar: null` removes the photo. A missing `avatar` field leaves it as it is. A missing `name` leaves the name as it is.
- When to send: once to every contact I have a 1:1 conversation with (`encrypt_for`) and once into every group (`group_encrypt`) when the photo or the name changes; to a new contact after the session opens (the first message received from that contact); into a group when I create it or am added to it, and again once when I see a member added to it (the newcomer has none of the earlier profiles). A client remembers, per contact and per group, the hash of the last profile it sent there, so it does not send the same profile twice otherwise. A contact I never wrote to gets nothing, so a profile never opens a session on its own.
- Receivers store it against the sender fingerprint (`from` of the InboundJson, also in groups, so members who are not contacts get a face too). It never shows a bubble, never counts as unread, never moves the conversation and never notifies. A known `avatar_hash` with the same value is a no-op.
- `name` renames the contact only when the person did not rename that contact locally.
- Clients that do not know the kind ignore it silently (section 1 rule).
- A photo taken with a caption is sent as the image message followed by a text message with the caption (no caption field on media).
- Avatars replace the initials wherever initials are shown: conversation list, chat header, group sender next to bubbles, contact detail, call screen, member lists, and on iOS the notification (communication notification with `INSendMessageIntent`, falling back to the initials).

### Group profile

There is no app-level group update message (group ops come out of the core as synthetic `group-op` messages and the core exposes no rename), so the group photo is a new kind sent with `group_encrypt`:

```
{ kind: "group-profile", group_profile: { name?: string, avatar?: "<base64 JPEG>" | null, avatar_hash?: "<hex sha256>" } }
```

- Same photo rules as `profile`. `name` is the display name of the group in every client (it overrides the name from the core op log).
- Accepted only from a group admin (`admins` in `groups()`), dropped otherwise. A system line says who changed it ("Inès a changé la photo du groupe.").
- The admin sends it when the group photo or name changes, and again (once) to the group after adding a member, so the newcomer gets it.

### Leaving a group

`leave_group` is local only in the core. Before calling it, a member sends into the group:

```
{ kind: "group-leave" }
```

Receivers show a system line ("Inès a quitté le groupe."). An admin who receives it calls `group_remove` for that member, so the sender key rotates and every member's list updates through the op log. The leaving member then deletes the conversation locally.

### Client behaviour that goes with it (no wire format)

- Conversation list: a conversation with a new message moves to the top with an animated reorder, shows the last message preview, its time, an unread badge and a bold title while unread. A new conversation (first message from a new contact, or a group I was added to) appears at the top at once.
- In-app banner: when a message arrives in another conversation than the one open, a glass banner slides in at the top (avatar, name, preview). Tap opens the conversation, swipe up dismisses, it hides after 4 s. Muted conversations show none.
- My card: one tap from the conversations screen opens my card full screen (large QR of the `relay1c:` link, photo, name), with Share (the link) and Scanner (the camera scanner). Scanning a card adds the contact and opens the chat.
- Search: the conversation list searches names and message text and highlights matches; tapping a message hit opens the chat at that message and flashes it. Inside a chat, a search bar steps up and down between hits with a "2 sur 7" count.
